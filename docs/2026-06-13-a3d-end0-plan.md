## Testbed regression (2026-06-13) + fix — the hsync-engine trigger feed

First deploy of `dbcb166` (all 3 roles restarted) left every AGENT peer
stuck at KNOWN: zero Hello/Beat ever sent (grep "hello" over the whole
agent log = 0 hits), leader-election storm (votes=1 expected=3). Infra
peers (combiner/signer) were fine — the OPERATIONAL seed worked.

ROOT CAUSE — the two-State-stores trap, in reverse. The hsync ENGINE
decides whether to send Hello/Beat in `hsync/hello.go`:
`agentNeedsHello` gates on `peer.{Api,Dns}Details.State == PeerStateKnown`
and `fastBeatAttempts` on `== PeerStateIntroduced` — i.e. the
`hsync.PeerDetails.State` NG store (Stage-D, correctly NOT touched by
END.0). That store is FED from `agent.{Api,Dns}Details.State` via the
bridge (`agentDetailsToHsync`/`syncHsyncPeerFromAgent`). END.0 deleted the
discovery/hello/beat writes to `agent.{Api,Dns}Details.State` (moved them
to `transport.Peer`), so the NG store never advanced past NEEDED →
`agentNeedsHello` always false → the engine never even CALLED
`SendHelloWithFallback`. The transport send-gate rework was never reached.
Local boundary tests missed it because they call SendHello* directly,
bypassing the engine's decision.

FIX (operator-approved option 1: re-feed the NG store via dual-write).
Restore the `agent.{Api,Dns}Details.State` writes alongside the
transport.Peer writes, at all four sites, each tagged "END.0 dual-write
(transitional, retire in Stage D)":
- discovery KNOWN (`agent_discovery.go`, API+DNS usable blocks),
- Hello success → INTRODUCED (`SendHelloWithFallback`, API+DNS),
- Beat success → OPERATIONAL (`SendBeatWithFallback`, API+DNS),
- inbound DNS hello → INTRODUCED (`routeHelloMessage`).
The bridge round-trips these to `hsync.PeerDetails.State` so the engine
trigger fires. transport.Peer remains canonical for reads/display/gossip/
send-gates/the derived top-level marker — the dual-write is ONLY the feed
to the not-yet-migrated hsync engine trigger.

RESIDUAL (Stage-D cleanup, track it): END.0 does NOT fully retire the
`agent.{Api,Dns}Details.State` writes — they survive as the engine-trigger
feed until Stage D / END.3 migrates `agentNeedsHello`/`fastBeatAttempts`
to read `transport.Peer`. The struct-field deletion was already A5, so no
new debt — just a clearly-marked transitional write.
Binding spec: v3 plan "A3d-END" (END.0 bullet) +
`2026-06-13-a3d-end-kickoff-handoff.md`. Verified against tip
tdns-mp `d8b1af6`, tdns-transport `892e5de` on 2026-06-13.

## Goal (restated)

Make the canonical `transport.Peer` State the SOLE functional per-peer
connection-state store, and retire the `agent.{Api,Dns}Details.State` +
`agent.State`/`LastState` sidecar AS A FUNCTIONAL STORE. The real prize:
make the MP-visible state DERIVED from the per-mechanism transport state,
not independently written — which structurally removes the
unconditional-write hazard behind last night's three bugs.

The READ side is already done (S1b): `peer list` + `gossip state` read
`transport.Peer` via `effectiveAgentState`→`EffectiveState()`
(`agent_view.go:122`) and the distrib display
(`apihandler_agent_distrib.go:369-374, 452-457`). END.0 closes the
WRITE side.

## *** Wire-DTO trap (Trap 3) — RESOLVED: it is a NON-ISSUE ***

The handoff note (Trap 3) and the v3 plan (END.0/END.1, S3 item-4
deferral) say END.0 must "feed the GetZoneAgentData wire DTO from
transport.Peer" or the CLI `peer status` Heartbeats line breaks.

**Verified false.** `Agent.MarshalJSON` (`agent_utils.go:463-491`)
serializes ONLY {Identity, InitialZone, ApiMethod, DnsMethod, Zones,
State, LastState, ErrorMsg} — it does NOT serialize `ApiDetails`/
`DnsDetails`, and there is no custom `Agent.UnmarshalJSON` nor any
`AgentDetails` (Un)MarshalJSON. So every agent crossing the wire to the
CLI arrives with `ApiDetails == nil`, `DnsDetails == nil`.

`PrintHsyncAgent` (`cli/hsync_cmds.go:530`) guards the Heartbeats line
with `if details == nil { continue }` (`:545`). So the
`SentBeats/LatestSBeat/LatestRBeat` line is **already dead over the
wire** — it never prints. All 4 callers of `PrintHsyncAgent`
(`cli/hsync_cmds.go:95,368,403` + `cli/agent_debug_cmds.go:220`) go
through this JSON round-trip.

The Heartbeats display that DOES work is a SEPARATE path —
`hsync-peer-status` → `HsyncPeerInfo` (`agent_structs.go`) backed by
HsyncDB, never AgentDetails.

**Consequence:** END.0 does NOT need a DTO-feed step. The 5 telemetry
fields + `ReceivedBeats` can stay as inert struct fields (deleted in A5
with the struct) with no wire/CLI consequence. This SHRINKS END.0 vs the
handoff note. (One honest cleanup option: since the Heartbeats line is

display polish, NOT END.0, and the v3 plan parks `peer list -v`
presentation as a post-A5 task. Out of scope here.)

## Proposed END.0 approach

Single commit (the load-bearing one), with its own `-race` + testbed
checkpoint before END.1. Net effect: the canonical transport per-mechanism
state drives the send gates and transitions; AgentDetails.State stops
being written; top-level agent.State stops being independently written.

### Step 1 — make `transport.Peer.State` (top-level) derived

`EffectiveState()` already does best-of-mechanisms with a fallback to
top-level `p.State` (`peer.go:237-261`). The hazard is the UNCONDITIONAL
top-level `SetState` writes (KNOWN at discovery, ERROR on discovery-fail)
that the fallback then surfaces.

Approach: keep the existing best-of-mechanisms `EffectiveState()`, but
make the discovery/error paths stop writing top-level `peer.State`
unconditionally. Concretely:
- Discovery KNOWN (`agent_discovery.go:333-334,366-367`): the guarded
  `if peer.GetState() < Known` promote stays as the DISCOVERY-PHASE
  marker (NEEDED→KNOWN is a phase, not a liveness state, and has no
  per-mechanism OPERATIONAL/DEGRADED/INTERRUPTED equivalent — so it
  legitimately lives top-level until a mechanism goes active). This is
  the one place top-level State is still written, and it is monotonic +
  guarded.
- `OnPeerDiscovered`/`OnDiscoveryFailed` guards (already present, mp
  `44f06bd`/`0bb1d5d`): re-audit. With KNOWN gated on a usable mechanism
  and ERROR not regressing an active peer, and with EffectiveState
  preferring any active per-mechanism state over top-level, the guards
  remain correct; simplify comments to point at the derived model. The
  unconditional ERROR write becomes harmless because an active mechanism
  outranks it in EffectiveState — but we keep the no-regress guard as
  defense-in-depth (cheap, already tested).

Result: top-level `peer.State` is only ever the discovery-phase marker
(NEEDED/KNOWN/ERROR pre-first-beat); once any mechanism beats
successfully, EffectiveState ignores top-level entirely. That is the
"derived" property the bug-root demands, achieved without a risky rewrite
of EffectiveState's signature.

### Step 2 — redirect the functional send-gates to read transport state

Add a small MP helper (in `agent_view.go`, next to the existing
mappers) that answers the send-gate predicates off the peer:
- `mechStateForGate(peer, mech) AgentState` — returns
  `transportToAgentState(peer.MechanismRawState(mech))` (RAW, not
  decayed: the gates are about "have we handshaked", not liveness; the
  decay belongs to the display/liveness read, and a DEGRADED/INTERRUPTED
  mechanism must still be beat-eligible, which raw OPERATIONAL gives via
  the existing 5-state OR — confirm semantics hold).

Then:
- `SendHelloWithFallback` API gate `:1508` / DNS gate `:1536`: read
  `mechStateForGate(peer,"API"/"DNS") == AgentStateKnown` instead of
  `agent.ApiDetails.State == AgentStateKnown`. On success, write
  `peer.SetMechanismState(mech, Introducing, ...)` (replacing the
  `agent.*Details.State = AgentStateIntroduced` twin). Skip-as-success
  + error-message reads (`:1572-1586`) read the peer.
- `SendBeatWithFallback` API gate `:1629` / DNS gate `:1668`: read the
  peer's raw mechanism state for the 5-state OR. The OPERATIONAL write
  already lands on the peer (`:1654-1655,1697-1698`); DELETE the
  AgentDetails twin (`:1643,1684`) and the AgentDetails telemetry bumps
  that are now display-dead (verify against the dead-wire finding before
  deleting `SentBeats++` etc. — they have no live functional reader after
  S3, but leave the FIELDS on the struct; just stop writing them if
  nothing reads them, or keep the writes harmlessly until A5 — DECIDE,
  see open question 1).
- Inbound hello (`:667-668,690`): the canonical
  `peer.SetMechanismState("DNS",Introducing)` already lands at `:657`;
  delete the AgentDetails twin writes. (Inbound API hello has no
  AgentDetails twin to delete — confirm the API inbound path writes the
  peer; if it does not, ADD `peer.SetMechanismState("API",Introducing)`
  for symmetry — this is a coverage gap to check.)

### Step 3 — redirect the functional top-level `agent.State` gates

- Deferred-task preconditions (`agent_utils.go:401,443,454`) and
  `apihandler_agent.go:383`: read `ar.effectiveAgentState(id)` /

- `peer reset` (`apihandler_peer.go:122-129`): the per-mechanism + top

  `peer.SetState(Needed,...)` + per-mechanism resets on the transport

### Step 4 — retire the RecomputeSharedZonesAndSyncState State flip

`agent_utils.go:63-78`: delete the `agent.State` LEGACY/OPERATIONAL
transition block; KEEP the `peer.ReplaceSharedZones` sync (zones still

`effectiveAgentState`.

### Step 5 — stop writing top-level `agent.State`/`LastState`

After Steps 1-4, the only remaining writers are the discovery struct-init

## Operator decisions (2026-06-13)

1. **Telemetry writes in the Beat success path: (a) DECIDED.** Leave the
   `SentBeats/LatestSBeat/LatestRBeat/ReceivedBeats/LastContactTime`
   field writes in place until A5 deletes the struct. END.0 deletes only
   the `.State` twin, not the telemetry bumps. Minimal diff, zero
   behavior change.

2. **State model: MARKER DECIDED.** Keep the existing
   best-of-mechanisms `EffectiveState()` with the top-level `p.State`
   fallback. Top-level `peer.State` is only the pre-first-beat
   discovery-phase marker (NEEDED/KNOWN/ERROR), written by the discovery
   paths only, guarded + monotonic. NO new `DiscoveryPhase` field, NO
   `EffectiveState` rewrite — the full phase/state separation is a tidy
   post-END.0 follow-up if ever wanted, NOT END.0. END.0 stays MP-side
   (the transport accessors it needs already exist).

3. **Inbound API hello coverage: VERIFY-AND-ADD DECIDED.** Confirm the
   inbound API hello path writes the canonical peer
   (`SetMechanismState("API",Introducing)`); if it does not, END.0 adds
   it for symmetry with the inbound DNS path (`:657`).

   **VERIFIED 2026-06-13 — the gap is REAL.** Both inbound hellos
   converge on `MsgQs.Hello`, but asymmetrically:
   - DNS: `routeHelloMessage` (`hsync_transport.go:640`) writes
     `peer.SetMechanismState("DNS",Introducing)` + `LastHelloRecv("DNS")`
     INLINE at the router (`:657-658`), then pushes a report with NO
     `Transport` field.
   - API: `APIhello` (`apihandler_agent.go:1206`) does NO mechanism-state
     write; it pushes a report with `Transport: "API"` (`:1264`) and
     relies on the consumer.
   - Consumers of `MsgQs.Hello` (agent `HelloHandler` via
     `adaptHelloReports`/`auditor_engine.go:163`; combiner
     `combiner_msg_handler.go:77`; signer `:62`) do NOT write per-mechanism
     state. `HelloHandler` (`hsync_hello.go:11`) is effectively a no-op
     for state.

   So after an inbound API hello, `peer.Mechanisms["API"].State` is never
   set to Introducing — only the DNS path writes (and it writes "DNS"
   unconditionally even when the hello arrived over API, because the DNS
   router assumes DNS).

   **END.0 fix (DECIDED: at producers).** Keep the inbound mechanism-state
   write at the two inbound entry points, NOT in the consumers:
   - DNS `routeHelloMessage` (`:657-658`): already writes the peer; keep
     it, just make it explicit `"DNS"` (it already is) and stamp the
     report `Transport:"DNS"` for consistency.
   - API `APIhello` (`apihandler_agent.go:1263`): ADD the symmetric
     `peer.SetMechanismState("API",Introducing)` +
     `SetMechanismLastHelloRecv("API")` write before pushing the report.
   This touches only the two Stage-A producer files and does NOT perturb
   the combiner/signer/auditor consumers (Stage C / C3 owns those). The
   AgentDetails.State twin writes at the DNS producer (`:667-668,690`) are
   deleted (the canonical write is the survivor). Lock order unchanged
   (transport.Peer self-locks; no registry mutex held across the write).
